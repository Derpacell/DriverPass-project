The Driverpass project was a course project that involved a lot of designing of a software over the span of 8 weeks. The goal was to help design a system for this hypothetical company that could help prep students for DMV driving tests. For this, it involved creating user levels, that would account for different roles who'd access the system, from as low as the student- to as high as the owner of a system. Every role played a significant part in keeping the system this constant flowing process. It was mean't to support students schedule appointments, account for available instructors and vehicles and so on. It was made to account for employee to manage customer accounts and to track said appointments. Then having a backdoor for IT to do maintenance on user accounts, while also having there be a role that goes even above them.

An aspect I actually enjoyed was organizing all of the requirements we were give. It was one of those things where you may know what needs to be done, but breaking down the order of when it needs to be done becomes its own thing. You realize you can't focus on things like security until you have users and the actual infrastructure for the system down. I also think the UML activity diagrams were useful because they demonstrated how the system should respond when something doesn't go as expected, such as an unavailable appointment or a customer attempting to access a practice test without the appropriate package. For this class we were to use LucidChart, but I had so many errors and issues that I just starting considering alternatives rather than beating the problem until I figured it out. https://app.diagrams.net Is a significantly more straightforward option, and I can't recommend it enough for it's straightforward usability. I don't think I'd revise anything about my processes besides planning my week to actually accommodate for the workload.

When interpreting the user's needs, I started by reviewing the client's interview and trying to identify the functions they expect the system to perform. I translated those expectations and standards into actual functioning and nonfunctionaling requirements, which help guide both the UML diagrams and technical design. If we start to consider the importance of user needs we see where our system needs to function correctly from a technical standpoint while still failing to solve the problems it was originally designed to address. The approach I took to software design is trying to understand the problem, then establishing the requirements before we finally decide how the system should be structured. Using a combination of process modeling and object-oriented modeling is beneficial because it allows me to examine both how the system operates and how its information is organized. In future projects, I'd continue using UML diagrams for the visual aid for those I'm explaining it to, analyzing the requirements, and direct feedback from users to identify potential problems before development begins. If this was in a group setting, everyone would always need to be on the same page, so making easily consumable media so everyone can stay on the same page.
